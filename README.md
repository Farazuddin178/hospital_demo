# Oxygen Hospital

A Next.js 14 (App Router) marketing site for a multi-specialty hospital group, built
around a "calm clinical" design language: pure white, warm paper greys, one muted
clinical blue, one gentle earth tone, and a lot of whitespace.

```bash
npm run dev      # http://localhost:3000
npm run build    # production build
npm run start    # serve the production build
npm run images   # re-download and re-encode the photography (see below)
npm run lint
```

---

## Design system

Tokens live in two places and nowhere else. Change them there and the whole site follows.

| Where | What it holds |
| --- | --- |
| `tailwind.config.ts` | The three palette ramps, shadows, radii, easing |
| `src/app/globals.css` | Surface/ink CSS variables, light/dark swap, component classes |

The palette keys are intentionally generic so pages never hard-code a hue:

- **`brand`** — muted clinical blue. Navigation, links, and the primary call to action.
- **`accent`** — gentle clay. Eyebrows, section rules, warmth. Never a large fill.
- **`teal`** — soft sage. Wellness cues, checkmarks, confirmations.

Every foreground/background pair used in the UI was measured against WCAG AA.
Body copy sits at 16.9:1, secondary text at 5.7:1, the primary button at 8.2:1.
Values annotated `// 4.3:1` or lower in the config are for icons, borders, and
large text only.

Reusable classes (`.btn-primary`, `.card`, `.eyebrow`, `.section-title`,
`.link-arrow`) are defined once in `globals.css`. Depth comes from hairline borders
rather than drop shadows, which is what keeps the page feeling clinical rather than
decorated.

### Typography

Inter for everything functional, Source Serif 4 for display only. Both are
self-hosted and subset by `next/font`, so there is no font-CDN request. The
generated fallback faces carry `size-adjust` metrics, so the swap from fallback to
web font produces no layout shift.

## Structure

```
src/
  app/
    page.tsx              homepage
    patients/page.tsx     "Patients & Visitors" mega-menu destination
    locations/page.tsx    "Locations" mega-menu destination
    specialties/          "Conditions & Treatments" destinations
  components/
    Header.tsx            mega-menu navigation (client component, see below)
    HeroSearch.tsx        hero search (client component)
    Photo.tsx             self-hosted responsive photography
    Footer.tsx
  lib/
    site-data.ts          original config: specialties, services, site config
    home-content.ts       homepage + navigation content, and the search index builder
    search.ts             search types and matcher — imports nothing, safe on the client
    image-manifest.json   generated by `npm run images`, do not edit by hand
```

### Navigation

The three mega menus were originally native `<details>`/`<summary>` elements, chosen
for zero-JS server-rendered menus. Real-device testing killed that approach: a touch
tap on `<summary>` fires a normal click event *without* the browser running its
native "toggle the details" activation, and separately, this app's React tree would
revert any `open` attribute set from outside it. Both are the same root problem —
nothing outside React can safely own DOM state that lives inside a hydrated React
tree. On a site whose visitors are mostly on phones, a menu that ignores taps is
disqualifying.

So `Header.tsx` is a client component and the open/closed state is ordinary React
state. Panels are conditionally rendered, so a closed menu is absent from the DOM
entirely rather than merely hidden. Escape (with focus return to the trigger),
outside-click dismissal, and closing on navigation are implemented explicitly, since
they no longer come free with `<details>`.

One layout constraint worth knowing: the panels use `inset-x-0` to span the full
viewport width, so their wrappers must **not** be `relative`. The containing block
has to stay the sticky `<header>`, or the panel collapses to the width of its
trigger button.

Menu column labels are `<p>` elements, not headings. The nav sits above the page's
`<h1>` in the DOM, so real headings there would put a dozen entries ahead of it in
the screen-reader outline. Grouping is carried by `aria-labelledby` instead.

**Anchor ids in `home-content.ts` are a contract with `/patients` and `/locations`.**
Renaming a section id without updating the menu leaves a dead link.

### Hero search

`HeroSearch.tsx` ships the search JavaScript. The index is built on
the server by `buildSearchIndex()` and passed down as a plain-data prop, so the
icon-laden content modules never reach the client bundle. Matching is synchronous
over ~69 in-memory entries, so there is nothing to debounce and no request to wait on.

The index maps symptoms to specialties, which is what makes it feel like it
understands the question: people type "chest pain", not "cardiology". Keyword
aliases mean "sugar" finds diabetes care and "telugu" finds a doctor who speaks it.

It implements the ARIA 1.2 combobox pattern: arrow keys, Enter, Escape, managed
`aria-activedescendant`, and a polite live region announcing the result count.

## Performance

Deliberate choices, in rough order of impact:

**The hero has no image.** The largest element above the fold is the headline, so
Largest Contentful Paint lands on text in the first frame with no image, font, or
network round trip in the way.

**No image optimizer in the request path.** Every photo is pre-encoded to WebP at two
fixed widths by `npm run images` and served from `/public/images` with a one-year
immutable cache. There is no `sharp` dependency, no optimizer server hop, and no
third-party image host. The rendered page makes **zero third-party requests**.

**No layout shift from photography.** `Photo.tsx` emits intrinsic `width`/`height`
from the manifest and paints the reserved box in the photo's own average colour,
computed at fetch time. The box is the right size and the right colour before a
single image byte arrives.

**`content-visibility` below the fold.** Sections carry `.defer-paint`, so the
browser skips layout and paint for off-screen content while keeping the scrollbar
honest via `contain-intrinsic-size`.

Measured on a production build of the homepage:

| Asset | Raw | Gzip | Brotli |
| --- | --- | --- | --- |
| HTML | 244 KB | 34 KB | 22 KB |
| CSS | 66 KB | 11 KB | 10 KB |
| JS (modern browsers) | 343 KB | 103 KB | 88 KB |
| Photography, mobile widths | | | 361 KB |
| Photography, desktop widths | | | 755 KB |

All photography is lazy-loaded and below the fold. The `polyfills` chunk is tagged
`noModule` and is never fetched by a modern browser.

### Known nit

`next/font` is not emitting `<link rel="preload">` for the font files in this setup
(the generated font manifest comes back empty regardless of `weight`, `subsets`, or
`className` versus `variable`). The practical cost is small: `display: swap` means
text paints immediately in a metric-matched fallback, so neither LCP nor CLS is
affected, and only the latin subset of each family is ever downloaded. Worth
revisiting on a Next.js upgrade.

## Refreshing the photography

`npm run images` re-downloads every photo, re-encodes it to WebP at both widths,
extracts the average colour, and rewrites `src/lib/image-manifest.json`. Edit the
`SET` array at the top of `scripts/fetch-images.mjs` to change a photo, its crop
ratio, its widths, or its alt text. Alt text lives in the manifest so it travels
with the image rather than being retyped at each call site.

Photos currently come from Unsplash. Swap the ids in that array for licensed
photography before launch.

## Hosting

One codebase, two builds:

| Command | Output | Use it for |
|---|---|---|
| `npm run build` then `npm start` | Node server | Render (`render.yaml`), or any host once the backend is in use. API routes, middleware and security headers all run. |
| `npm run build:static` | Plain files in `./out` | GoDaddy shared hosting (cPanel / Linux). No server. |

Server-only code stays in the repo for later: `src/middleware.server.ts` and
`src/app/api/**/route.server.ts`. Only the server build includes `.server.ts` files
(see `pageExtensions` in `next.config.mjs`), so the static build skips them.
`public/.htaccess` handles security headers, caching and the 404 page on Apache. The
HTTP-to-HTTPS redirect is cPanel's "Force HTTPS Redirect" switch (Domains), turned on
after AutoSSL has issued the certificate.

### Forms on the static build

On GoDaddy the contact and appointment forms post to `public/api/*.php`, which
email each submission to info@oxygen-hospital.com (GoDaddy Professional Email).
GoDaddy's cPanel hosting blocks website code from reaching outside mail servers,
so the mailer hands messages to the hosting account's own mail server
(`localhost:25`), which passes them on to Professional Email. Two cPanel settings
make that work:

- **Email Routing** for `oxygen-hospital.com` set to **Remote Mail Exchanger**.
- The SPF record includes the hosting server: `v=spf1 ip4:118.139.182.121 include:secureserver.net -all`.

The mailbox password (GitHub secret `SMTP_PASSWORD`) is only used if the site
moves to a host that allows outside mail connections. See the comments at the top
of `public/api/_mailer.php` for the order it tries routes in and how to read its
diagnostics. If sending fails, the form offers the phone number and a pre-filled
WhatsApp message instead.

To point the forms at a separate backend later, set `NEXT_PUBLIC_API_URL`; it must
accept `POST /contact` and `POST /book-appointment` with the same JSON.

### GitHub to GoDaddy

`.github/workflows/deploy-godaddy.yml` runs on every push to `main`. It builds the
static site and uploads `out/` over FTP. Until the FTP secrets are set it only builds.

1. Point the domain at the hosting, then in cPanel open SSL/TLS Status and click
   Run AutoSSL. When the domain shows a valid certificate, turn on Force HTTPS Redirect
   under Domains. Create an FTP account (FTP Accounts) with access to `public_html`.
2. In GitHub: Settings > Secrets and variables > Actions. Add the secrets `FTP_SERVER`,
   `FTP_USERNAME` and `FTP_PASSWORD`. Add the variable `SITE_URL`, for example
   `https://www.yourdomain.com`.
3. Push to `main`, or run the workflow from the Actions tab.

If FTPS is refused, set the variable `FTP_PROTOCOL` to `ftp`. To upload by hand
instead, run `npm run build:static` and upload the contents of `out/` (including the
hidden `.htaccess`) to `public_html` with cPanel File Manager.
